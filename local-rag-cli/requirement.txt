================================================================================
MULTI-DOCUMENT SESSION & DYNAMIC CRUD ARCHITECTURE
================================================================================

1. Multi-Document Session Workspace:
------------------------------------
In this architecture, a ChromaDB collection is not limited to a single file.
Each session functions as a multi-document workspace containing PDFs, code files,
and plain text documents simultaneously.

                       ┌──────────────────────────────────────────────┐
                       │        SESSION COLLECTION (e.g. 'Project')   │
                       └──────────────────────┬───────────────────────┘
                                              │
          ┌───────────────────────────────────┼──────────────────────────────────┐
          │                                   │                                  │
          ▼                                   ▼                                  ▼
  [ Document A: spec.pdf ]           [ Document B: guide.pdf ]          [ Document C: main.py ]
   ├── Chunk 1 (Page 1)               ├── Chunk 1 (Page 1)               ├── Chunk 1 (Class)
   ├── Chunk 2 (Page 1)               ├── Chunk 2 (Page 2)               └── Chunk 2 (Function)
   └── Chunk 3 (Page 2)               └── Chunk 3 (Page 2)

2. Metadata-Driven Isolation & Collision Prevention:
----------------------------------------------------
Every indexed chunk is tagged with immutable metadata:
- source_file  : Normalized absolute path (e.g. C:/Users/Docs/spec.pdf)
- file_name    : Basename for human display (spec.pdf)
- file_type    : Content category ('pdf' | 'code' | 'text')
- page         : 1-indexed page number (isolated strictly per page)
- chunk_index  : Sequential chunk counter across document
- paragraph_idx: Sequential paragraph counter within page
- char_count   : Verified text length

* Path-Hash ID Addressing:
  To prevent collisions when two documents from different folders have the same
  filename (e.g. /Desktop/notes.txt vs /Downloads/notes.txt), vector IDs use:
  ID = {session_name}_{basename}_{path_hash8}_c{chunk_index}

3. Dynamic CRUD Operations Lifecycle:
-------------------------------------
- Multi-Doc Append : User selects an existing session during ingest; new chunks are
                     appended with file-level identity.
- Smart Upsert     : When re-ingesting an updated file, ChromaDB automatically purges
                     stale chunks matching that source_file before indexing new splits,
                     ensuring ZERO duplicate chunks.
- Selective Purge  : col.delete(where={"source_file": path}) surgically removes ONLY
                     that document's vectors while keeping all other documents intact.
- Storage Vacuum   : SQLite WAL checkpoint (PRAGMA wal_checkpoint(TRUNCATE)) and
                     VACUUM are executed after deletes to guarantee immediate physical
                     disk reclamation without storage bloat.


================================================================================
SOURCE CITATIONS, GROUNDING & VERIFICATION ARCHITECTURE (PHASE 4)
================================================================================

1. Balanced Grounding & Zero-Extrapolation Prompting:
-----------------------------------------------------
To prevent hallucination while maintaining conversational helpfulness, the system
prompt enforces balanced context constraints:
- "Answer BASED on the provided context. Ground every factual claim directly in the context."
- "If the information is partially relevant, use it and be explicit about what the context does and does not say."
- "Only if there is absolutely nothing related to the question, say so clearly: 'I cannot find that information in the document.'"
- "Do NOT invent data, formulas, or outside details that are not in the context."
- "CITATION REQUIREMENT: After every factual statement, append its source citation tag in brackets (e.g. [Source 1], [Source 2])."

2. Grounded "Verified Sources" Panel (core/citations.py):
---------------------------------------------------------
Immediately following each streamed answer, a structured table renders the exact
sources used:
- Tag         : [Source 1], [Source 2], etc.
- Location    : Document filename, 1-indexed page (for PDFs), paragraph number.
- Excerpt     : Clean preview snippet showing the exact text retrieved from the document.

3. Windows Desktop Cross-Verification (Interactive Slash Commands):
-------------------------------------------------------------------
Users can interact with citations directly inside the chat loop:
- /open <N>    : Executes Windows `os.startfile()` to launch the exact PDF or text
                 document in the user's default Windows application (Adobe Acrobat,
                 Edge, or Notepad) for instant cross-verification.
- /source <N>  : Opens a detailed panel displaying the complete, uncropped chunk text,
                 character count, and full disk path.
- /sources     : Re-prints the full source verification table for the previous answer.
- /help        : Displays all interactive commands.

4. Prefill Latency UX (Live Spinner to Typewriter Transition):
--------------------------------------------------------------
During prompt prefill and vector retrieval (~10s on CPU), a live animated Rich dots
spinner keeps the user informed: "Searching documents & preparing response...".
The exact millisecond token #1 arrives, the spinner cleanly clears and switches
seamlessly to real-time typewriter token streaming.

================================================================================
PHASE 6: CPU-GUARDRAILED CONVERSATIONAL MEMORY & ANAPHORA RESOLUTION
================================================================================
Motivation & Problem Solved:
---------------------------
Previously, every user question was evaluated as an isolated 1-turn interaction.
Follow-up questions ("What is her email?", "Summarize that policy", "Why?") failed
because vector retrieval could not resolve pronouns without context, and the LLM
had no record of previous dialogue turns.

Critical Real-World Constraint: CPU Burn & Thermal Throttling Protection:
------------------------------------------------------------------------
Running on consumer laptops (CPU-only, no VRAM offload) means every additional prompt
token increases prompt-prefill latency (TTFT) and CPU package heat. Naively appending
full conversation transcripts causes:
1. Prefill time skyrocketing from 2s to 12s+.
2. CPU thermal throttling (dropping clocks from 4.0GHz to 1.8GHz).
3. Token generation rate collapsing from 14 tok/s to 6 tok/s.

Engineered Architecture & Decisions:
-----------------------------------
1. Zero Extra LLM Calls (core/memory.py):
   Avoided running a secondary LLM "query rewriter" step, which would double inference
   time and burn CPU. Instead, a lightweight heuristic anaphora detector (<0.01ms)
   identifies pronouns and short follow-up queries, enriching the ChromaDB search query
   with the prior turn's subject without any model invocation.

2. Strict Sliding Window & Character Budgeting (core/config.py):
   - MAX_HISTORY_TURNS = 3 (sliding window of last 3 user-assistant interaction pairs).
   - MAX_HISTORY_CHARS = 750 (hard ceiling for formatted history in the prompt).
   - MAX_ASSISTANT_SUMMARY_CHARS = 200 (compresses previous AI replies in memory,
     stripping citation tags to avoid prompt token waste).
   - Context budget balanced to MAX_CONTEXT_CHARS = 3000.
   Total prompt never exceeds ~850 tokens, keeping CPU prefill under 2.5s warm.

3. Interactive Session Management (tui/menu.py):
   - /history : Displays previous dialogue turns in the current session.
   - /clear   : Resets conversation memory for the session without affecting documents.

================================================================================
PHASE 7: DENSE + LEXICAL BM25 HYBRID SEARCH & RECIPROCAL RANK FUSION (RRF)
================================================================================
Motivation & Problem Solved:
---------------------------
Dense vector retrieval (ChromaDB + Nomic embeddings) excels at high-level semantic
concepts, but frequently struggles with exact alphanumeric strings, error codes
(e.g., ERR_403_SEC), acronyms, and exact function names. Hybrid search solves this
by running both dense vector search and BM25 lexical keyword matching concurrently,
fusing results using Reciprocal Rank Fusion (RRF).

Critical Real-World Hardware & Latency Protections:
--------------------------------------------------
1. Sub-Millisecond Search Latency:
   - BM25 index build time on session chunks: ~15 milliseconds on the very first query.
   - BM25 search latency on subsequent queries (cache hit): ~0.1 milliseconds (<0.001s).
   - Zero perceptible delay added to the user's interaction loop.

2. Zero-Memory-Leak LRU Session Cache (core/hybrid_search.py):
   - BM25 indexes are cached in an `OrderedDict` LRU cache bounded to `MAX_CACHED_SESSIONS = 5`.
   - If a user navigates between 10+ different document sessions, older session indexes
     are automatically evicted from RAM, preventing memory accumulation.
   - When documents are ingested or deleted, cache invalidation is triggered automatically
     in `core/database.py`.

3. Reciprocal Rank Fusion Formula:
   RRF_Score(d) = sum( 1.0 / (60 + Rank_i + 1) )
   Documents appearing in both Dense and BM25 lists are boosted to the top rank, ensuring
   the LLM context receives the most factually and lexically precise chunks.

4. Self-Contained Query Guard & Anaphora Isolation (core/memory.py):
   - Eliminated false-positive query contamination where interrogatives ('what', 'how')
     or determiners ('this doc') combined previous topics into independent questions.
   - Preserved true personal pronouns ('he', 'she', 'it', 'they') and elliptical follow-ups
     ('why?', 'what about salary?', 'and the timeline?').
   - Self-Contained Guard: Queries with explicit alphanumeric codes (e.g., SPA-2026-C)
     or explicit doc indicators are protected from topic contamination.

5. Identifier Priority & Prompt Scope Hardening (core/rag_engine.py, core/hybrid_search.py):
   - When a query contains an explicit ID or document indicator, BM25's #1 exact match
     is prioritized at Rank 1 in RRF fusion.
   - Prompt rules explicitly forbid the LLM from re-answering, summarizing, or reconciling
     prior dialogue topics, restricting conversation history strictly to background pronoun reference.

================================================================================
PHASE 8: DYNAMIC MULTI-MODEL REGISTRY & RUNTIME SWAPPING (QWEN 2.5 & PHI-3)
================================================================================
Motivation & Problem Solved:
---------------------------
Fixed LLM definitions force users to choose between high latency on modest CPUs
or lower reasoning capabilities. To optimize for 8GB RAM laptop hardware while
retaining flexibility, the application now supports runtime switching between
modern small language models (SLMs).

Supported Models:
- Qwen 2.5 (1.5B): Ultra-fast prompt prefill (~3.2s) and low RAM footprint (~1.1GB).
  Default model optimized for responsive TTFT on consumer laptop CPUs.
- Phi-3 (3.8B): Standard RAG model for deeper reasoning contexts (~2.4GB RAM).

Architecture & Implementation:
1. Dynamic Model Registry (core/config.py):
   - `get_active_model()` and `set_active_model(tag)` manage the global active model.
   - `SUPPORTED_MODELS` registry maps models to user-friendly descriptions.
2. Runtime Swapping:
   - Main Menu: Direct option to switch models anytime:
     "Switch Active AI Model (Current: qwen2.5:1.5b)"
   - Interactive Chat Command: `/model` allows switching models in the middle of a
     chat session without dropping vector session context or conversation memory.
3. Dynamic Health Verification (core/health.py):
   - Startup health checks adaptively verify that the active model is installed in Ollama.
